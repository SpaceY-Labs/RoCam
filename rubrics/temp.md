## 1. What the presentation says the project is

At the highest level, RoCam is presented as a **high-performance, low-cost, autonomous rocket tracking platform** for hobbyist and collegiate rocketry. The presentation frames the system as an answer to three constraints:

- rockets are too fast for manual optical tracking
- commercial systems are too expensive
- student teams need something deployable, not just a lab proof-of-concept

The D2 final presentation consistently pushes three claims:

1. **Autonomous edge AI tracking**
   The system detects the rocket locally on a Jetson Orin Nano, without cloud dependence.

2. **High-speed closed-loop control**
   The presentation repeatedly emphasizes 60 Hz control, low latency, and the idea of "zero perceived latency" through a shader-first preview path plus slower physical gimbal correction.

3. **Accessibility**
   The target BOM is under 500 CAD, which is positioned as the main differentiator against commercial systems in the 5,000-10,000+ CAD range.

### Presentation-structure analysis

The HTML presentation is not just a content file; it also reveals what the team thinks matters most:

- Slides 1-4 establish the problem, affordability argument, and team roles.
- Slide 5 is the live demo breakpoint, meaning the project is intended to be shown as a real integrated system, not a concept.
- Slides 6-11 focus heavily on CV, data, and ML, which shows the detector and dataset were central technical risks.
- Slides 12-15 pivot into architecture, operator software, and recording workflow, showing the project is treated as a full product, not a model-only pipeline.
- Slides 16-19 emphasize testing, scalability, stakeholder feedback, and polish, which suggests the team wanted to prove engineering maturity rather than only raw tracking performance.

### Slide-by-slide content interpretation

The final deck communicates these features and priorities:

- **Challenge**: rockets at extreme speed, small visual footprint, unaffordable commercial alternatives.
- **Solution**: autonomous tracking, 60 Hz closed-loop gimbal control, low BOM.
- **CV pipeline**: CSI capture, GPU downsampling/letterboxing, YOLO26s, best-detection selection, P-control, GL shader.
- **Zero-latency tracking story**: fast software crop/zoom for operator perception while the gimbal physically catches up.
- **RoCam Labeler**: custom annotation platform, implying they did not rely on an off-the-shelf labeling workflow.
- **ML training**: H100 training, custom augmentations, COCO negatives, deployment-aware model selection.
- **Fault-tolerant architecture**: isolated processes and shared memory.
- **Mission Control UI**: live preview, manual override, telemetry, bilingual support.
- **Recording workflow**: raw capture plus telemetry first, stabilized replay later.
- **Testing**: strong emphasis on automated tests and CI.
- **Future scalability**: 4K, larger gimbals, multi-camera, weatherproofing, mobile UX, analytics.
- **Stakeholder feedback**: direct product changes from operator feedback, especially drag-to-move control and improved status visibility.

## 3.2 Deployment and hardware platform

Across the docs, the core deployment platform is:

- **NVIDIA Jetson Orin Nano**
- **STM32F405-based custom control PCB**
- **camera sensor via CSI**
- **HDMI output**
- **networked browser-based operator interface**
- **gimbal-mounted optical system**

### Hardware role split

- The **Jetson** is the compute host.
- The **STM32 PCB** is the real-time motion-control endpoint.
- The **camera** feeds raw frames into the Jetson CV/media pipeline.
- The **gimbal + servos** physically track the target.
- The **browser client** is the operator console.

### Circuit stack from the PCB report

The circuit design report describes a benchtop development PCB with:

- USB-C PD input at 20 V / 3.25 A
- one 17 V rail for the Jetson
- two independent 5.5 V rails for pan and tilt servos
- STM32F405 powered from the Jetson 3.3 V rail
- UART communication between Jetson and STM32
- PWM servo outputs from the STM32

Key selected components:

- **STM32F405RG**
- **TPS54308** buck converters
- **HUSB237** USB PD controller

### Why this stack matters

This is not a pure software project. The hardware stack is chosen to separate:

- high-level AI/media work on the Jetson
- deterministic low-level actuation on the STM32

That is the right split for a tracking system where Linux-class compute is useful, but servo timing and low-latency control should not depend on a Python event loop.

## 3.3 Backend / control-plane stack

The backend is a **Python-based control system** running on the Jetson.

### Confirmed stack

From docs plus source/manifests:

- Python 3.10+ (`INSTALL.md`)
- Flask
- Flask-CORS
- pyserial
- netifaces
- PyGObject / GStreamer bindings
- `jetson-stats` / `jtop` style system telemetry integration
- Python multiprocessing
- shared memory IPC
- Server-Sent Events (SSE)

### Architectural structure

The backend is explicitly decomposed into:

- **CV process**
- **Live video process**
- **Transcode process**
- **Control process**

The MG and Reflect-and-Trace docs both emphasize this as a deliberate evolution away from a monolithic process.

### Actual implementation responsibilities

The backend handles:

- gimbal commands
- arming/disarming
- manual move and manual move-to
- focal-length control
- recording lifecycle
- recording database and metadata
- status aggregation
- process orchestration
- serving the frontend SPA
- real-time status streaming
- real-time log streaming
- stabilized preview/download transcoding

### Why this stack is well chosen

Python is a practical coordination language here because:

- the media/CV heavy lifting is offloaded to DeepStream/GStreamer/TensorRT
- Flask is enough for a local operator API
- the most latency-sensitive motor work is moved to firmware

So Python is acting more like a **system orchestrator** than a raw signal-processing engine.

## 3.4 CV and runtime media stack

This is the most technically distinctive stack in the project.

### Core runtime stack

- NVIDIA DeepStream
- GStreamer
- TensorRT FP16 inference
- YOLO26s in deployed form
- CSI camera input
- GPU letterboxing / downsampling
- OpenGL shader path for live zoom/stabilization behavior

### CV pipeline as documented

The D2 presentation, ML report, MG, and backend source all support a pipeline like this:

1. camera capture at 1080p60
2. GPU preprocessing / letterboxing to approximately 540x960
3. YOLO26s inference via TensorRT FP16
4. best single detection selection
5. P-control / tracking command generation
6. GL shader-driven preview cropping/zoom
7. HDMI/live-preview output

### Key design choices

- **NMS-free one-to-one detection head**
  The ML report makes this a major selling point. It reduces post-processing latency and simplifies deployment behavior.

- **Single-target assumption**
  The entire runtime path assumes one rocket per frame. This allows the system to discard multi-object complexity and choose the highest-confidence detection.

- **GPU-only fast path**
  The docs repeatedly emphasize keeping decode, preprocessing, inference, and visual output on GPU as long as possible.

### Why this stack is a strong fit

For this project, the biggest CV problem is not generic object detection; it is **tiny-object detection under hard real-time constraints**. DeepStream + TensorRT + an NMS-free architecture is a coherent answer to that constraint.

## 3.6 Firmware / embedded stack

The firmware is a separate and serious subsystem, not a toy sketch.

### Confirmed stack from `src/pcb-firmware`

- Rust 2024 edition
- `embassy-executor`
- `embassy-stm32`
- `embassy-time`
- `embassy-sync`
- `cortex-m`
- `cortex-m-rt`
- `defmt` / `defmt-rtt`
- `panic-probe`
- STM32F405 target

### Firmware responsibilities

From the docs and source:

- receive host commands over UART
- expose a gimbal RPC server
- clamp and apply requested pan/tilt angles
- maintain current tilt/pan/focal values
- drive servo PWM tasks
- control ARM and status LEDs
- respond to host queries for gimbal info, pose, focal length, and GPS placeholders

### Protocol design

The gimbal protocol is impressively formalized for a capstone:

- CRC-8/SMBUS
- explicit request/response model
- fixed command IDs
- typed payloads
- timeout and invalid-ack behavior

Supported command families:

- gimbal info
- arm LED
- status LED
- set/get angle
- set/get focal length
- get GPS data

### Why this stack matters

The firmware is what turns the project from "Jetson demo" into an actual cyber-physical system. The use of Rust + Embassy suggests the team wanted:

- predictable concurrency
- hardware-level clarity
- safer low-level code than C

That is a strong engineering decision for a control board.

## 4.4 Recording and media features

The recording system is one of the better-designed parts of the repo.

### Key recording design

RoCam does not try to render the final polished replay while the launch is happening. Instead it:

- records a raw video stream to `video.avi`
- writes per-frame telemetry to a log file
- reconstructs stabilized playback later

### Recorded data includes

- pan
- tilt
- focal length
- FPS
- timestamps
- stabilization transforms

### Benefits of this design

- lighter critical-path capture during launch
- richer post-flight analysis
- ability to re-render preview/download later
- better separation of real-time and archival concerns

### Additional robustness features

From source and V&V evidence:

- download/preview activity can pause and resume pipeline behavior safely
- recording database protects against path traversal
- recording-only backend mode exists
- the system attempts to remain stable if the CV process restarts during recording

This is a mature recording architecture for a capstone project.

## 5. System architecture and data flow

## 5.1 End-to-end path

A good way to understand RoCam is as a layered path:

1. **Perception input**
   Camera captures 1080p60 frames.

2. **GPU media/CV path**
   DeepStream/GStreamer preprocesses frames, runs TensorRT inference, and exposes preview/livestream branches.

3. **Tracking logic**
   Control logic consumes the selected detection and computes target pan/tilt behavior.

4. **Transport layer**
   Commands move over UART to the STM32 using the documented packet protocol.

5. **Embedded actuation**
   Firmware clamps, stores, and applies requested pan/tilt/focal states to the servos and indicators.

6. **Operator observability**
   Browser UI receives status and logs, renders preview, and exposes controls.

7. **Archival path**
   Video and telemetry are stored separately and re-rendered later through a transcode pipeline.

## 5.2 Why the architecture is strong

The architecture is strong because it respects different time domains:

- GPU/media timing
- UI/operator timing
- serial command timing
- servo actuation timing
- post-processing timing

Instead of forcing everything into one process or one runtime model, the project separates these concerns.

## 7. Weaknesses, gaps, and documentation inconsistencies

This is the most important critical section. The repo is strong, but the docs are not perfectly aligned.

## 7.1 The OpenAPI spec is outdated relative to the implementation

`docs/Design/EndpointsSpecification/openapi.yaml` does not match the actual backend/API client.

### Examples

- It documents `POST /api/status` returning a snapshot.
- The actual backend exposes `GET /api/status` as an SSE stream.
- It does not document `/api/logs`.
- It does not document `/api/set_focal_length`.
- It does not document stabilized preview/download endpoints.
- Its `StatusResponse` schema is much smaller than the real one used by the frontend.
- It documents raw MP4 download behavior, while the current UI/backend use stabilized preview/download endpoints that stream WebM.

This is a significant documentation gap because the API spec is supposed to be the contract between backend and frontend.

## 7.2 ML documentation is internally inconsistent

The repository contains multiple different "final model" stories.

### One story

The final presentation and `docs/Extras/MachineLearning/MLReport.tex` present **YOLO26s** as the surviving deployed model:

- DS mAP50-95 = 0.631
- DS small mAP = 0.341
- roughly 9% deployment loss
- P2 rejected due to FP16 sensitivity

### Another story

`docs/V3_Training_Pipeline.md`, `docs/ReflectAndTrace/ReflectAndTrace.tex`, and `docs/Presentations/D3_EXPO/expo.tex` still describe **YOLO26s-P2 / V3-Phase2** as the advanced or final model, with materially different metrics.

### Interpretation

The team clearly iterated fast and changed model-selection conclusions over time, but the repo no longer communicates one unambiguous final answer across all documents.

## 7.3 The User Guide is effectively empty

`docs/UserGuide/UserGuide.tex` is still template-level and contains no real operating instructions.

This matters because the project otherwise places strong emphasis on:

- operator workflow
- usability
- safety
- recordings
- field deployment

The lack of a completed user guide is one of the clearest holes in the docs set.

## 7.4 Some environmental assumptions conflict

There is a mismatch between documents on operating conditions:

- SRS physical environment requirement: `0C to 45C`
- Hazard Analysis assumptions: `10 to 25 degrees Celsius`

The circuit report partly resolves this by saying the prototype PCB is for development/testing, not the final field platform, but the inconsistency still creates ambiguity.

## 7.5 Frontend tooling guidance is inconsistent

The frontend documentation and manifests are not perfectly synchronized:

- `INSTALL.md` uses `npm`
- `src/react-app/README.md` uses `yarn`
- the labeling app uses `pnpm`

This is not fatal, but it makes the repo feel like three adjacent toolchains rather than one unified developer experience.

## 7.6 Some presentation/supporting README files are still placeholders

Examples:

- `docs/Presentations/D2_FinalPresentation/README.md` is still template text
- the User Guide is unfilled

That weakens the "polished final package" impression despite the strong technical core.

## 7.7 The labeling-app design doc does not fully match current routes

The design doc describes:

- `POST /projects/:projectId/locks/acquire`
- `POST /projects/:projectId/locks/release`

The actual backend uses:

- `POST /projects/:projectId/locks`
- `DELETE /projects/:projectId/locks`

This is a smaller issue than the main API mismatch, but it shows the same broader synchronization problem.

## 8. Overall assessment

RoCam is best understood as a **full-stack embedded vision product**, not just a detector, a website, or a gimbal.

Its major technical stacks are:

- edge AI deployment on Jetson
- Python process orchestration and API serving
- GStreamer/DeepStream/TensorRT media and inference runtime
- React/TypeScript operator software
- Rust/Embassy STM32 firmware
- custom annotation/data tooling on Firebase
- benchmark/training infrastructure on H100
- formal verification, protocol, and documentation artifacts

Its major feature groups are:

- autonomous rocket tracking
- manual override and operator control
- live preview and telemetry
- raw recording plus deferred stabilized replay
- dataset creation and SAM-assisted labeling
- fault isolation and process recovery
- protocol-level gimbal control
- safety-oriented state transitions and error visibility
- automated testing and CI

### Final judgment

The project is technically ambitious and, more importantly, **architecturally coherent**. The strongest evidence of maturity is that the team solved problems across the entire lifecycle:

- collecting the right data
- training a model that survives deployment
- moving detections into real hardware commands
- giving operators a usable interface
- recording and replaying events
- testing the system systematically

The biggest weakness is not the engineering itself. It is that the documentation package is **slightly out of sync with the final implementation state**, especially for:

- API surface
- final ML model selection
- user-facing operating documentation

If those synchronization gaps were cleaned up, this would read as a very strong and unusually complete capstone system.
