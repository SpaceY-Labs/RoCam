\section{Document Evaluation}

\subsection{SRS Evaluation}

\subsubsection{Abstraction}
The SRS was reviewed to ensure requirements describe \textit{what} RoCam must do
from a stakeholder/operator perspective (camera operator, rocketry team) rather
than \textit{how} it is implemented (specific CV models, firmware details, or UI
framework choices). Overall, the Functional Requirements (FRs) are written at a
suitable level of abstraction: they describe externally observable behaviours
such as acquiring frames, displaying a live preview, allowing manual control,
tracking/arming transitions, and recording management.\\

The Non-Functional Requirements (NFRs) were also reviewed and are generally
abstract (e.g., usability, performance, safety, reliability). Where an NFR
implicitly assumes a particular technical solution (e.g., a specific fps target
or a specific latency measurement method), this is acceptable if the SRS also
defines a clear, measurable fit criterion.

\subsubsection{Testability}
The FRs are mostly testable because they describe observable outcomes that can be
checked via logs, UI state, or recorded artifacts (e.g., a created video file).
However, due to the final project scope constraint that \textbf{only unit testing
is executed} (and system/field tests are out of scope), some FRs are not directly
testable end-to-end within this iteration. To preserve testability under the
reduced scope, FR evaluation in this project is performed through:
\begin{itemize}
  \item Unit tests for isolated logic (e.g., state transitions, validation, file
        naming/path logic, error formatting),
  \item Component-level tests where a module boundary exists (e.g., UI state
        reducers, API request formatting, parsing),
  \item Stakeholder review feedback for user-facing correctness/priority (without
        live flight validation).
\end{itemize}
For the NFRs, testability varies:
\begin{itemize}
  \item \textbf{Performance}: testable if the SRS states measurable thresholds
        (e.g., 1080p60 I/O, latency targets), but in this project we can only
        partially test performance via unit/component tests and profiling of
        specific pipelines rather than full system measurement.
  \item \textbf{Usability}: testable through walkthrough protocols and checklists
        (screenshots, task completion observations), but results are less precise
        than instrumentation-based studies.
  \item \textbf{Safety}: testable for software guards (confirmation prompts,
        manual arming only, safe idle transitions) via unit tests and static
        inspection; physical safety behaviours at the gimbal/hardware layer are
        limited by out-of-scope hardware validation.
\end{itemize}

\subsubsection{Ambiguity}
The SRS wording is largely clear, but several items can be improved to reduce
interpretation differences during verification:
\begin{itemize}
  \item \textbf{Terms that need operational definitions:} phrases such as
        ``real-time'', ``smooth'', ``fluid'', ``clear error message'', and
        ``maintains lock'' should map to concrete thresholds (fps, latency,
        allowed dropped frames, maximum time-to-reacquire, required UI elements).
  \item \textbf{State-related FRs:} FRs related to \textit{armed}, \textit{tracking},
        and \textit{idle} benefit from explicitly defining entry/exit conditions and
        time bounds (e.g., ``within 2\,s of sustained loss, transition to idle'').
  \item \textbf{Recording management:} where FRs mention ``download'' or ``list'',
        the expected metadata should be explicit (name format, timestamp source,
        duration computation, sorting rule).
\end{itemize}
These ambiguities do not block implementation but do increase the risk of
disagreement during V\&V. Where possible, they are handled in this project by
encoding assumptions as unit-testable acceptance criteria.

\subsubsection{Completeness}
For completeness, we reviewed whether the SRS covers the primary stakeholder
goals for RoCam: acquisition, operator control, automated tracking behaviour,
recording workflow, and safe operation. At a high level, the SRS is close to
complete for Rev0 scope. The main completeness concerns arise from:
\begin{itemize}
  \item \textbf{Out-of-scope verification constraints:} since system tests and
        field tests are not executed in this iteration, any FR/NFR that requires
        integrated hardware measurement (true end-to-end latency, outdoor
        robustness, real launch tracking) cannot be fully verified. The SRS
        should explicitly mark such requirements as requiring future work or
        later verification stages.
  \item \textbf{Third-party dependencies:} camera/gimbal behaviour is assumed
        per manufacturer documentation; the SRS should clarify which behaviours
        are \textit{assumed} vs \textit{verified by this team}.
  \item \textbf{Safety and hazard linkage:} any hazard mitigations (e.g.,
        emergency stop, confirmation prompts, manual arm gating) should be
        explicitly referenced in either FRs or NFRs so that traceability from the
        Hazard Analysis to requirements is direct.
\end{itemize}

\subsubsection{Spelling and Grammar}
A pass over the SRS found no major grammar defects; remaining issues are
primarily minor consistency fixes (capitalization, hyphenation, consistent use
of abbreviations such as ``UI'', ``fps'', ``gimbal''). In the final report, we
standardize terminology across documents (SRS/MG/MIS/VnV Plan/Report) to reduce
confusion during traceability review.

\subsubsection{Ease of Understanding}
The SRS is readable and structured, but ease-of-understanding can be improved by:
\begin{itemize}
  \item Making requirement IDs clickable links in the PDF (or ensuring the
        traceability tables include enough context so readers do not need to
        search manually).
  \item Adding brief legends/notes to diagrams (if any) explaining symbols and
        data flow, especially when multiple modules interact (Jetson pipeline,
        STM32 controller, UI).
  \item Including a short glossary of user-facing terms (armed/tracking/idle,
        ``preview'', ``overlay'', ``recording'') so interpretation is consistent.
\end{itemize}

\subsection{Design Evaluation}

\subsubsection{Consistency With Requirements}
We reviewed MG/MIS against the SRS to ensure that each major requirement has a
clear design owner (vision pipeline, control firmware/interface, UI/recording).
Overall, the decomposition is aligned with RoCam’s core functions. The main
design-to-requirement risk is where requirements imply integrated behaviour
(e.g., tracking quality under occlusion) but the design only specifies unit-level
behaviour without an executable integration test under the current scope.

\subsubsection{Modularity and Interfaces}
The design is modular across the main subsystems (vision, control, UI). Interfaces
should remain stable and well-documented (commands, telemetry, timing, and error
reporting). This modularity supports unit testing under the constrained scope by
allowing logic verification at module boundaries even when system tests are not
executed.

\subsubsection{Maintainability}
Maintainability is supported by separation of concerns and internal review via
pull requests. The main maintainability improvement opportunity is to enforce
consistent error/telemetry schemas between backend and frontend so tests and logs
remain stable as features evolve.

\subsection{Verification and Validation Plan Evaluation}

\subsubsection{Completeness}
The VnV Plan contains detailed system test descriptions; however, the finalized
scope explicitly states that \textbf{only unit testing and stakeholder review are
in scope}. Therefore, completeness in the plan must be interpreted as:
\begin{itemize}
  \item System tests retained for traceability/reference only (not executed),
  \item Executed evidence coming from unit tests and review artifacts.
\end{itemize}
To avoid mismatch with the report, the report will clearly label which planned
tests were executed and which were not, and will provide unit-test evidence that
covers the same FR intent where feasible.

\subsubsection{Unambiguous}
The plan is mostly unambiguous, especially where checklists specify concrete
actions. Ambiguity exists mainly where system tests describe qualitative outcomes
(e.g., ``smooth'', ``clear error message'') without explicit acceptance criteria.
Where those tests are not executed, ambiguity is reduced by replacing them in the
report with unit-testable criteria or explicit ``not executed'' markings.

\subsubsection{Feasibility}
The plan is feasible under the revised scope because it limits execution to unit
tests and stakeholder review. Any activities requiring live rocket launches,
hardware field conditions, or external reviewers are explicitly excluded. This
prevents over-claiming and keeps V\&V achievable within available time and access.

\subsubsection{Overall Objective Accomplishment}
Under the revised scope, the plan still supports the core objectives:
\begin{itemize}
  \item \textbf{Document confidence:} internal checklist-based review and
        traceability tables improve confidence in SRS/design consistency.
  \item \textbf{Nonfunctional focus:} selected NFRs (e.g., usability walkthrough,
        performance characterization at module level) can be partially supported
        with evidence, with limitations clearly stated.
  \item \textbf{Implementation confidence:} unit tests provide concrete,
        repeatable evidence that critical logic behaves as expected.
\end{itemize}
Any objectives requiring integrated hardware validation are explicitly deferred
and documented as future work rather than claimed as completed.

defined in the \SRS{}. Test procedures and test case definitions are specified in
the \VnVPlan{}; to avoid unnecessary repetition, this report focuses on
\textbf{execution status}, \textbf{results}, and \textbf{evidence}.

\subsection{Scope and Execution Policy}
\label{sec:fr_scope}

As stated in the latest \VnVPlan{} (Revision 5.0), the only testing executed for
this project is \textbf{unit testing} and a \textbf{stakeholder review}
(McMaster Rocketry Team). Integration/system/field tests are documented in the
plan for traceability but are \textbf{not executed} due to resource and contact
constraints.

\subsection{Unit-Test Evidence for Functional Requirements}
\label{sec:fr_unit_evidence}

Because system-level FR tests were not executed, FR verification relies on unit
tests that validate the underlying behavior (e.g., state transitions, command
validation, recording pipeline logic, UI action handlers). Evidence is presented
in two parts:

\begin{enumerate}
  \item \textbf{Requirement-to-test mapping:} Section~\ref{sec:trace_reqs} lists
  which unit tests support each FR.
  \item \textbf{Execution results:} Section~\ref{sec:unit_testing} reports
  pass/fail status and, where applicable, links to CI logs or local test output.
\end{enumerate}

\subsubsection{Evidence Format and Reproducibility}
For each functional requirement verified by unit testing, the report records:
\begin{itemize}
  \item The FR identifier(s) from the \SRS{}.
  \item The unit test file(s) / test case names (self-descriptive naming).
  \item The execution outcome (pass/fail) for the final submission revision.
  \item A pointer to evidence (CI job log, screenshot, or attached test report).
\end{itemize}

\subsection{Stakeholder Validation Touchpoint}
\label{sec:fr_stakeholder_touchpoint}

Stakeholder validation is performed via a review session with the McMaster
Rocketry Team as defined in the \VnVPlan{}. The outcomes of this review (action
items, approvals, and required changes) are summarized in
Section~\ref{sec:changes_due_testing}. Any requested changes are tracked as
GitHub Issues and linked there to maintain traceability.
